# Shared Value Pack and booking management

- Customer `/membership`, product details, purchase checkout, renewal preview and active-wallet queries do not request or inherit a playing branch. These public `/memberships` APIs ignore a stale `X-Branch-ID`; authentication/ownership checks remain in the handlers. Online purchase invoices keep the existing central accounting default in the schema; this is internal sales attribution, not a playing-location restriction. Admin/cashier sales still retain their sales-branch accounting context. Legacy eligible-branch mappings no longer restrict the product catalogue or shared quota. Sport rules still apply: Padel quota is shared between Cemara and S. Parman, and Tennis courts remain Cemara-only.
- Customer catalogue shows both sports without a branch choice. Membership tariff descriptions explain that playing date/location determines applicable hours. Membership invoice pages do not present the internal sales location as the playing location. Actual booking usage history continues to show the court's location.
- Booking management uses the same membership classification for badges as the existing regular/membership filter: a membershipUserId or positive membershipSessionsUsed indicates Membership. Future recurring reservations with a wallet ID and zero debits are Membership. A customer merely owning a package does not make every booking Membership. Mixed checkouts with membership usage are classified Membership, consistent with the existing filter/export.
- Kelola Pemesanan → Tunggakan Value Pack shows negative quota across the shared customer wallet, independent of the purchase branch. The ordinary transaction list/export defaults to `balance=nonnegative`; the separate monitor uses `balance=negative`. It is read-only; debt settlement still happens through the existing paid-renewal flow. Its export uses the same negative/global scope. Existing branch ownership of individual invoices and admin mutations is retained.
- GET `/courts/booking-window` returns inclusive WIB `startDate`/`endDate` plus `months`. The upper boundary is the longest configured rolling horizon among the selected branch/sport's active courts, or the final published manual slot for non-rolling courts. A court without published future manual slots no longer silently adds three months. With no future schedule, the boundary is today. Client dates wait for this response, trim stale out-of-range selections and guard cart continuation. Calendar month/year dropdowns cannot navigate beyond the boundaries; unsupported months are omitted. Slot claiming still enforces each court's own rolling horizon on the server.

No schema migration is required for these changes.
